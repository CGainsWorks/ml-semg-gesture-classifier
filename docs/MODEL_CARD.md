# Model card: sEMG gesture classifier

## Model details

| | |
| --- | --- |
| Task | 18-class gesture classification from a 200 ms window of 16-channel surface EMG |
| Architecture | Three Conv2d-BatchNorm-ReLU-MaxPool blocks over a 16 x 40 electrode-by-time image, then two dense layers |
| Implementations | TensorFlow 2.18 and PyTorch 2.6, from one shared `ArchitectureSpec` |
| Parameters | 177,490 trainable |
| Multiply-accumulates | 7,764,224 per inference |
| Input | `(16, 40)` float32, per-channel standardised using statistics from the training fold |
| Output | 18 logits; softmax applied by the caller |
| Deployment formats | TFLite float32 and full-integer int8; ONNX float32 and statically quantised int8 |
| Training data | Ninapro DB5, exercise B, 10 intact-limbed adults |
| Licence | Code MIT. The training data is research-use only and is not redistributed. |
| Version | 1.0.0 |

The exact numbers this card quotes are regenerated by `make demo` and land in
`results/db5/export_report.json`, `analysis/db5/summary.json` and
`benchmarks/`. The README's tables are checked against those files by
`python -m src.check_readme`, which CI runs.

## Intended use

**This is a portfolio and research artefact.** It exists to demonstrate the
full path from a public sEMG dataset to a quantised model inside a stated
latency budget, and to report the subject-independent result honestly.

One result worth carrying away before any of the rest: on this dataset a
random forest over seventeen hand-designed features per channel is more
accurate within subject than either neural network, by fourteen points. The
networks justify themselves only at the calibration condition, where they take
personalisation far better. If you are reaching for a network on an sEMG
problem, measure the classical baseline first.

Reasonable uses:

* A baseline or starting point for sEMG gesture-classification research.
* A worked example of subject-independent evaluation on Ninapro.
* A worked example of quantising a small model to int8 for both TFLite Micro
  and ONNX Runtime, and of measuring a control-loop latency budget rather than
  asserting one.
* Teaching material for myoelectric control.

## Out-of-scope use

**Do not put this in a medical device.** Not as a component, not as a
prototype that might become one, not "just for the first version".

Specifically:

* **It is not a medical device and has no regulatory clearance.** Not
  FDA-cleared, not CE-marked, not assessed under IEC 62304 or ISO 14971.
* **It was never trained or tested on an amputee.** DB5 is ten intact-limbed
  adults. Residual-limb sEMG differs in amplitude, in which muscles survive,
  and in how reliably a requested movement can be produced. Nothing here is
  evidence about the population a prosthesis is for.
* **The subject-independent accuracy is not good enough to control an
  actuator that could hurt someone.** Read the README's headline number and
  the false-activation rate together before considering anything else.
* **It has no safety layer.** No confidence gating, no watchdog, no fault
  detection, no safe-state behaviour, no fail-safe on sensor dropout. A
  prosthetic controller needs all of those and none of them is in scope here.
* **It has never been evaluated in closed loop with a user.** Offline
  classification accuracy and usable control are different things.

## Training

| | |
| --- | --- |
| Optimiser | AdamW, learning rate 1e-3, weight decay 1e-3 |
| Batch size | 256 |
| Epochs | up to 60, early stopping on validation accuracy with patience 8 |
| Dropout | 0.4 |
| Augmentation | Additive Gaussian noise (sd 0.15) and per-channel gain jitter (sd 0.25) |
| Validation split | 20% of training repetitions, split by whole (subject, repetition) group |
| Seed | 20250821 |
| Window geometry | 200 ms window, 50 ms stride, no majority vote |

Both frameworks take identical values, including the augmentation, which comes
from one shared NumPy implementation. That is what makes the framework
comparison a comparison of frameworks rather than of two different recipes.

Dropout is 0.4 rather than something smaller because the network overfits this
dataset badly without it. `experiments/architecture_comparison.py` measures
the train-test gap for each variant.

## Evaluation

Three protocols, defined in
[`EVALUATION_PROTOCOL.md`](EVALUATION_PROTOCOL.md):

1. **Within-subject.** Repetitions 1, 3, 4 and 6 train; 2 and 5 test. Per
   subject, averaged over ten.
2. **Subject-independent.** Leave one subject out, ten folds. **This is the
   headline.**
3. **Subject-independent plus calibration.** Leave one out, then fine-tune on
   one repetition from the held-out subject, test on the rest.

Reported: accuracy, balanced accuracy, macro F1, Cohen's kappa, per-class
precision and recall, confusion matrices, and separately the **false
activation rate** (rest classified as a movement, so the arm moves unbidden)
and the **missed activation rate** (movement classified as rest).

The current numbers are in the [README](../README.md) and in
`analysis/db5/EVALUATION.md`.

### Quantisation

Accuracy is measured through the deployed runtimes, one window at a time, on
held-out repetitions. The int8 and float32 figures and the size ratio are in
`results/db5/export_report.json` and in the README's deployment
table.

### Latency

Measured on the development machine, single-threaded, batch size one, reported
as a distribution. On-target figures for an STM32F411, an STM32H743 and a
Jetson Nano are **estimates**, computed from the MAC count with documented
assumptions, and every one is labelled `"measured": false`. No such board was
used. For the STM32F411 there is also an emulator estimate: the int8 model in
TensorFlow Lite Micro with CMSIS-NN, run under Renode, whose outputs match the
desktop interpreter bit for bit. See [`LATENCY_BUDGET.md`](LATENCY_BUDGET.md)
and [`benchmarks/README.md`](../benchmarks/README.md).

## Factors that affect performance

| Factor | Effect | Evidence |
| --- | --- | --- |
| **Subject identity** | The largest single factor by far. Cross-subject balanced accuracy is roughly half the within-subject figure for every model tried. | The README's gap table |
| **Model family** | Decides the within-subject result and not the cross-subject one. A random forest on hand-designed features leads within subject at 0.730; all four models tie between 0.312 and 0.321 across subjects. | The README's results table |
| **Gesture** | Wrist rotations separate well. Finger configurations that share a muscle group confuse with each other. | The per-class table and the confusion matrices |
| **Electrode placement** | Not measurable here: DB5 has one armband position per subject. Expected to matter a great deal. | Not measured. Stated as a limitation. |
| **Calibration data** | One repetition from the new wearer recovers 51% to 54% of the gap for the networks, 33% for the random forest and 9% for the linear discriminant. This, not accuracy, is what justifies a network here. | The `+ calibration` column |
| **Window length** | 200 ms and 250 ms are tied over ten folds (0.22 standard errors apart); 200 ms is 50 ms cheaper. Longer misses the budget. | `experiments/latency_accuracy_tradeoff.py` |
| **Stride** | 50 ms beats 25 ms at four of five window lengths. The extra windows a shorter stride buys overlap by seven eighths. | Same |
| **Majority vote** | Buys nothing measurable at this window overlap, so the default is not to vote. | Same |
| **Quantisation** | Small accuracy cost, roughly 3x size reduction. | `export_report.json` |

## Ethical considerations

**Population representation.** Ten subjects, eight male and two female, ages
22 to 34, forearm circumference 22 to 28.5 cm, all right-handed, all
intact-limbed. That is not a representative sample of anyone, least of all of
prosthesis users. Any performance claim from this model is a claim about ten
young adults with intact arms.

**The population this pretends to serve is absent from the data.** This is the
central ethical problem with the whole project and it is worth stating rather
than burying. The stated application is prosthetic control; the subjects have
both arms. Ninapro DB3 and DB7 include amputee subjects and are where this
should go next.

**Consent and provenance.** The recordings were collected by the Ninapro
project under their own ethical approval, from consenting adult volunteers,
and are published de-identified. No personal recordings were made for this
repository.

**Failure modes have asymmetric cost.** A prosthetic hand that closes when the
wearer did not ask it to is dangerous in a way that a hand which fails to
close is not. That is why the false-activation rate is reported separately
from accuracy rather than folded into it.

**Data drift.** sEMG shifts with fatigue, sweat, limb position and how the
electrodes were put on that morning. A model trained on one session and
deployed unchanged will degrade, and nothing here measures how fast.

## Caveats and recommendations

* Read the subject-independent number, not the within-subject one.
* Read the false-activation rate alongside accuracy.
* If you are building on this, get amputee data. It changes the problem.
* If you are deploying anything like this, add confidence gating, a watchdog
  and a defined safe state before anything else.
* Re-measure the latency on your own hardware. The estimates here are
  arithmetic, and the input/output allowance is an assumption.
